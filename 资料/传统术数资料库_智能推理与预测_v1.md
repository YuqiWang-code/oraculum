## 0. 文档定位、边界与可信度说明

这份资料库把《周易》、梅花易数、六爻纳甲、干支历法、二十四节气、六神 / 六兽、六亲、伏神、常见神煞以及风水的主要分支整理成**可计算、可配置、可追溯**的知识结构。

必须区分三类内容：



1. **古典文献内容**：例如《周易》的六十四卦、卦辞、爻辞，《说卦》《系辞》，以及后世术数文献中的术语。

2. **传统术数规则**：例如纳甲、八宫、世应、六亲、六神、月建、旬空、梅花体用等。不同流派会有差异，软件必须记录 “规则版本”。

3. **现代软件解释层**：例如把多条传统规则汇总成 0–100 分，再映射为 “大凶、凶、平、吉、大吉”。这是本项目的产品规则，**不是古籍原有的统一量表，也不是科学预测模型**。

建议在应用首页、结果页和 “关于” 页固定注明：

> 本应用用于传统文化研究、娱乐与自我反思，不代表客观事实或未来必然结果。涉及医疗、法律、财务、安全、升学就业等重要决定时，应以现实证据和专业意见为准，不以占卜结果替代决策。

心理学中的 Barnum/Forer effect 提醒我们：人容易把较笼统的描述理解为 “特别适合自己”。因此解释文本应尽量展示**规则依据和推导链**，避免故意使用模糊、制造恐惧或绝对化的断言。

# 1. 术数体系地图：不要把不同体系混成一个黑箱

## 1.1 《周易》经传层

核心对象：



* 阴爻、阳爻。

* 八卦。

* 六十四卦。

* 卦辞、爻辞。

* 《彖》《象》《系辞》《说卦》《序卦》《杂卦》等解释传统。

软件上应将 “经典原文” 和 “现代解释” 分开存储：



```
interface ClassicText {

&#x20; source: string

&#x20; original: string

&#x20; modernSummary: string

&#x20; tags: string\[]

}
```

不要把现代网站的二手解说冒充为 “古籍原文”。

## 1.2 梅花易数层

特点：



* 适合 “当下时间 / 数字 / 外应” 起卦。

* 重点是本卦、互卦、变卦、体卦、用卦以及五行生克。

* 适合本项目的 “打开手机，输入所问之事，按当前时间自动起卦” 的主入口。

## 1.3 六爻 / 文王卦 / 火珠林体系

特点：



* 每一爻装地支、五行、六亲、六神。

* 使用八宫、世应、纳甲、日辰、月建、旬空、动爻、变爻、伏神等。

* 更强调 “所问何事 → 取用神 → 看旺衰生克 → 看动变” 的结构。

本项目建议把六爻作为 “高级排盘” 模式，不要和梅花易数规则静默混用。

## 1.4 神煞层

“神煞” 不是一个全古籍统一、全流派一致的固定表。不同体系会使用不同神煞。软件必须：



* 标记神煞属于哪个体系；

* 标记按 “日干 / 日支 / 年支 / 月支” 等哪一项查；

* 标记来源；

* 默认作为**低权重辅助信息**，不可仅凭一个神煞直接判 “大吉 / 大凶”。

## 1.5 风水层

风水需要空间输入，如：



* 房屋坐向；

* 门、床、灶位置；

* 罗盘方位；

* 建造 / 大装修时间；

* 外部道路、水体、建筑形势等。

仅有 “当前时间 + 问题 + 姓名 / 代号” 并不足以严谨运行风水模块。因此 v1 可把风水作为资料库 / 知识阅读模块；未来用户录入方位数据后再计算。

# 2. 阴阳、八卦、五行：所有后续算法的基础

## 2.1 阴爻与阳爻

软件建议用统一二进制约定：



* 阳爻 `1`

* 阴爻 `0`

* 六爻数组始终采用**自下而上**：`[初爻, 二爻, 三爻, 四爻, 五爻, 上爻]`

例如乾卦为 `[1,1,1,1,1,1]`，坤卦为 `[0,0,0,0,0,0]`。

这一点必须写进单元测试，因为很多程序 bug 都来自 “图形显示从上往下、数组计算从下往上” 的方向混淆。

## 2.3 五行

相生：

`木 → 火 → 土 → 金 → 水 → 木`

相克：

`木克土、土克水、水克火、火克金、金克木`

建议代码不要散落 if/else，而是配置化：



```
const GENERATES = { 木: '火', 火: '土', 土: '金', 金: '水', 水: '木' }

const CONTROLS  = { 木: '土', 土: '水', 水: '火', 火: '金', 金: '木' }
```

# 4. 干支、时间与二十四节气

## 4.1 十天干与十二地支

十天干：

`甲 乙 丙 丁 戊 己 庚 辛 壬 癸`

十二地支：

`子 丑 寅 卯 辰 巳 午 未 申 酉 戌 亥`

天干与地支依次配对形成六十甲子，起于甲子。

## 4.2 地支五行常用映射



* 寅卯：木

* 巳午：火

* 申酉：金

* 亥子：水

* 辰戌丑未：土

## 4.3 24 节气

二十四节气是基于太阳周年运动的传统时间知识系统，2016 年列入 UNESCO 人类非物质文化遗产代表作名录。

常用顺序：

`立春、雨水、惊蛰、春分、清明、谷雨、立夏、小满、芒种、夏至、小暑、大暑、立秋、处暑、白露、秋分、寒露、霜降、立冬、小雪、大雪、冬至、小寒、大寒`

软件不要使用 “固定日期硬编码”；节气交接是具体天文时刻，应由历法库计算。

## 4.4 六爻月建：以 “节” 换月

常用规则：



| 月建 | 起点 | 终点 |
| -- | -- | -- |
| 寅月 | 立春 | 惊蛰 |
| 卯月 | 惊蛰 | 清明 |
| 辰月 | 清明 | 立夏 |
| 巳月 | 立夏 | 芒种 |
| 午月 | 芒种 | 小暑 |
| 未月 | 小暑 | 立秋 |
| 申月 | 立秋 | 白露 |
| 酉月 | 白露 | 寒露 |
| 戌月 | 寒露 | 立冬 |
| 亥月 | 立冬 | 大雪 |
| 子月 | 大雪 | 小寒 |
| 丑月 | 小寒 | 立春 |

交节前后可能跨月建，因此结果页应显示**精确交节时间、当前节气、当前月建**。

## 4.5 软件时间边界必须可配置

传统术数常见争议包括：



* 日界按 00:00 还是子初 23:00；

* 是否使用真太阳时；

* 所在时区；

* 海外用户是否仍按北京时间。

本项目默认建议：



* 默认时区：`Asia/Shanghai`；

* 默认按手机当地时区显示，同时允许手动切换；

* 排盘设置中提供 “日界规则” 选项；

* 结果里完整保存当次设置，保证未来复盘可重现。

# 5. 梅花易数：适合 “当前时间自动起卦” 的主模式

## 5.1 核心对象

一次梅花结果至少包含：



* 本卦；

* 互卦；

* 变卦；

* 动爻；

* 体卦；

* 用卦；

* 体用五行关系；

* 当前节气与时间信息；

* 所问类别；

* 解释证据链。

## 5.2 常见 “年月日时起卦” 版本

梅花易数存在不同传承和现代实现。软件不要写成 “唯一正确算法”，而应明确规则版本。

可把下面这一常见实现固化为：

`meihua_time_v1`

步骤：



1. 将年支编号设为：子 1、丑 2、寅 3…… 亥 12。

2. 取农历月数 `M`、农历日数 `D`、时支数 `H`。

3. `A = 年支数 + M + D`

4. `B = 年支数 + M + D + H`

5. 上卦数 `upper = A mod 8`，余 0 视为 8。

6. 下卦数 `lower = B mod 8`，余 0 视为 8。

7. 动爻 `moving = B mod 6`，余 0 视为 6。

8. 按先天数映射：1 乾、2 兑、3 离、4 震、5 巽、6 坎、7 艮、8 坤。

9. 改变对应动爻得到变卦。

10. 互卦常由本卦二三四爻构成下互、三四五爻构成上互。

特别要求：把这个算法版本写入结果记录，例如：



```
{"castingMethod":"meihua\_time","ruleVersion":"meihua\_time\_v1"}
```

## 5.3 体用

常见处理：



* 动爻所在的经卦部分为 “用”，另一部分为 “体”；具体细则可能有流派差异。

* 体代表主体 / 自身，用代表所问之事或外在作用。

* 体用之间以五行生克比和观察大势。

典型方向性规则可配置为：



* 用生体：偏有助力；

* 体克用：主体较能掌控；

* 体用比和：偏协调；

* 体生用：主体付出 / 泄耗；

* 用克体：主体承压。

不要只靠这一条就下最终判断，仍要综合本卦 / 互卦 / 变卦与问题语义。

## 6.4 六亲

以本卦所属 “宫” 的五行为 “我”：



* 生我者：父母

* 同我者：兄弟

* 我生者：子孙

* 我克者：妻财

* 克我者：官鬼

六亲不是现实亲属的固定直译，而是 “关系类别”。

### 常见问题语义映射



| 问题类型             | 常见首要用神候选 | 备注           |
| ---------------- | -------- | ------------ |
| 财务 / 收益          | 妻财       | 还需看世爻、子孙、兄弟等 |
| 工作职位 / 考试中的职位性目标 | 官鬼       | 文书考试也常同时看父母  |
| 合同、证件、论文、考试材料    | 父母       | 文书 / 凭证语义    |
| 项目产出、作品、解忧       | 子孙       | 语义随场景变化      |
| 竞争、同伴、团队         | 兄弟       | 可为助力也可为分耗    |
| 问自己整体状态          | 世爻       | 不等于只看一个六亲    |

软件必须先识别 “所问事项类别”，再取用神；不能先看到某六亲就决定吉凶。

## 6.5 六神 / 六兽

固定循环：

`青龙 → 朱雀 → 勾陈 → 螣蛇 → 白虎 → 玄武`

按占日天干决定初爻起点：



* 甲乙日：初爻青龙

* 丙丁日：初爻朱雀

* 戊日：初爻勾陈

* 己日：初爻螣蛇

* 庚辛日：初爻白虎

* 壬癸日：初爻玄武

然后自初爻向上按固定顺序循环。

建议软件把六神视为 “事件风格 / 附加象意”，权重低于：



1. 用神；

2. 世应；

3. 日月旺衰；

4. 动变；

5. 生克合冲。

不要设计 “见白虎必凶、见青龙必吉” 之类的单标签规则。

## 6.6 伏神

常见规则思路：



* 若本卦六爻中缺少某一类需要观察的六亲；

* 参考该卦所属宫的本宫纯卦，在对应爻位寻找该六亲；

* 隐伏者称 “伏神”，当前卦对应覆盖之爻常称 “飞神”。

不同文献对伏神旺衰、飞伏关系处理存在细节差异。建议：



```
interface HiddenSpiritRule {

&#x20; ruleVersion: string

&#x20; source: string

&#x20; palacePureHexagramLookup: boolean

}
```

v1 只负责**正确定位伏神**，解释权重从低到中，避免过度复杂。

# 11. 五档评分：“大凶、凶、平、吉、大吉”

这五档是产品需要的统一输出，因此必须写成**现代规则引擎**，并显示 “为何得到这个分”。

## 11.1 建议分数区间



* 0–19：大凶

* 20–39：凶

* 40–59：平

* 60–79：吉

* 80–100：大吉

为了避免 “临界点 59/60 产生巨大心理差异”，UI 同时显示：



* 分数；

* 五档标签；

* “证据一致性”；

* 有利 / 不利项数量；

* 规则版本。

## 11.2 六爻评分建议（v1）

满分基准 50，再叠加证据：

### A. 用神强弱：±18



* 得月建生扶：+6

* 得日辰生扶：+5

* 得动爻有效生扶：+4

* 明显受月日克制 / 冲破：对应扣分

* 空亡等不直接 “一票否决”，应按规则组合处理

### B. 世爻与用神关系：±10



* 用神生世、世用协调：正向

* 用神强力克世且问题语义不利：负向

* “世克用” 在不同问题中含义不同，不机械当吉

### C. 动变趋势：±12



* 动爻 / 变爻形成持续支持：正向

* 由旺转衰、由助转克：负向

* 多动爻相互矛盾时降低 “证据一致性”

### D. 卦辞 / 卦象总体：±6

只做中等权重，不压过用神体系。

### E. 六神 + 神煞：总计最多 ±4

保证辅助标签不会控制最终结果。

## 11.3 梅花评分建议（v1）



* 体用关系：±16

* 变卦对体的关系：±12

* 互卦过程：±6

* 本卦总体主题：±8

* 动爻文本与所问事项匹配：±6

* 时间 / 节气背景：±2

基准 50，最后 clamp 到 0–100。

## 11.4 五档标签的语言规范

禁止：



* “百分之百会失败”

* “你命里注定……”

* “一定有灾”

* 用恐吓方式催促付费或采取行为

建议：



* “按本次所选传统规则，结果偏‘吉’”

* “目前有利信号多于制约信号”

* “结果存在相互矛盾的证据，因此置信度较低”

* “可把它作为反思提示，而不是现实决定的替代品”

# 13. 风水资料框架

## 13.1 主要思路

可粗分：



* **形势 / 形法**：观察山水、道路、建筑、开口、空间关系；

* **理气**：使用方位、时间、八卦、九宫、罗盘等模型；

* 后世又发展八宅、玄空飞星、三合等多种体系。

不要在软件里把所有流派混成同一 “风水分数”。

## 13.2 二十四山

360° 分为 24 个山，每山约 15°。常见顺序按八方三山：



* 北：壬、子、癸

* 东北：丑、艮、寅

* 东：甲、卯、乙

* 东南：辰、巽、巳

* 南：丙、午、丁

* 西南：未、坤、申

* 西：庚、酉、辛

* 西北：戌、乾、亥

未来风水模块输入必须是 “方位角 + 磁偏角 / 真北设置 + 测量方式”，不能只让用户随便选一个 “东南”。

## 13.3 八宅

常见分类：



* 东四：坎、震、巽、离

* 西四：乾、坤、艮、兑

常见八游年名称：

`生气、天医、延年、伏位、绝命、五鬼、六煞、祸害`

这些属于传统术数名词，不宜把 “天医” 解释成医学效果，也不应给出 “某方位能治疗疾病” 的健康承诺。

## 13.4 三元九运 / 玄空

近现代常见分期：



* 一运 1864–1883

* 二运 1884–1903

* 三运 1904–1923

* 四运 1924–1943

* 五运 1944–1963

* 六运 1964–1983

* 七运 1984–2003

* 八运 2004–2023

* 九运 2024–2043

截至 2026 年，按该传统分期处在九运。该结论属于玄空风水内部的传统时间框架，不代表科学因果。

## 13.5 风水模块的 v1 边界

v1 仅做：



* 知识阅读；

* 方位与二十四山查询；

* 八卦方位图；

* 用户手工记录坐向。

v2 再考虑：



* 八宅；

* 九宫；

* 玄空；

* 房间平面图；

* 罗盘传感器。

这样同一条历史记录半年后仍能重现，而不会因为代码更新 “自动变卦”。

# 15. 知识库工程化：MD 只是源，程序应转成结构化数据

不要让前端每次运行都直接解析整份 Markdown 来算卦。

建议：



```
资料/\*.md

&#x20;  ↓（开发时人工/脚本整理）

src/data/

&#x20; trigrams.ts

&#x20; hexagrams.ts

&#x20; palaces.ts

&#x20; najia.ts

&#x20; sixRelations.ts

&#x20; sixSpirits.ts

&#x20; shensha.ts

&#x20; solarTerms.ts

&#x20; fengshui.ts

&#x20;  ↓

src/engine/

&#x20; calendar/

&#x20; meihua/

&#x20; liuyao/

&#x20; scoring/

&#x20; interpretation/
```

Markdown 用于：



* 追溯来源；

* 给开发者和 AI 读；

* 保存规则说明。

TypeScript 常量 / JSON 用于：



* 实际计算；

* 类型检查；

* 单元测试；

* 性能和稳定性。

# 18. 本项目推荐的 v1 功能范围

为了先做出 “真的能在手机用” 的版本，建议 v1 只实现：



1. 当前时间自动获取；

2. 输入所问之事；

3. 姓名 / 代号、性别可选；

4. 自动显示干支、农历、节气；

6. 本卦、互卦、变卦和动爻；

7. 经典卦辞 / 动爻辞；

8. 现代解读；

9. 五档评分；

10. 高级模式：六爻纳甲、世应、六亲、六神、伏神、旬空；

12. 离线可用；

13. 数据导出 / 导入；

* 八字命盘全套；

* 用户登录与服务器数据库。

先把核心规则做准，再扩展。
