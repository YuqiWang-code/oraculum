# 0. 先说结论

现有项目已经具备“经典资料层 → 确定性规则引擎 → 本地解释/评分层”的正确架构，但当前起卦入口确实偏单一：

- 默认只有“梅花易数·时间起卦”；
- UI 的 `datetime-local` 当前只保存到分钟；
- `castMeihuaByTime()` 只使用“年支 + 农历月 + 农历日 + 时支”，同一个时辰内结果不会因为分钟、秒而变化；
- `CastingMode` 类型虽然已经预留 `liuyao_coins`、`hybrid_experimental`，但 UI 还没有真正实现这些入口；
- README 也把“三枚钱法 / 纯手动录入 UI”列为后续 TODO。

因此 v2 建议做两层扩展：

1. **六种可独立使用的起卦方式**；
2. 额外提供一个 **“六源合参（实验）”**，把六类输入同时采集，形成一个现代、可重现、可解释的综合起卦过程。

六种独立方式建议为：

1. 秒级时间起卦；
2. 随机数起卦；
3. 摇骰子起卦；
4. 三枚钱六爻起卦；
5. 文字 / 字数起卦；
6. 外应起卦（颜色 / 物象 / 方位）。

注意：传统文献并没有“秒级时间”“浏览器随机数”“虚拟骰子”“六源合参”这一整套现代软件方案，因此必须区分：
- **传统直接规则**
- **传统规则的现代数字化实现**
- **本项目实验扩展**

绝不能把产品自定义规则伪装成古籍原法。

# 1. 网络调研：梅花易数本来就不只有“时间起卦”

## 1.1 《梅花易数》卷一：年月日时

《中国哲学书电子化计划》和维基文库所收《梅花易数》卷一都记载了常见的年月日时取数：

- 年支取 1–12；
- 农历月、日取数；
- 年月日总数除 8 定一卦；
- 加时支后再除 8 定另一卦；
- 总数除 6 取动爻。

这正是当前项目 `meihua_time_v1` 的来源。

来源：

- https://ctext.org/wiki.pl?chapter=867487&if=gb&remap=gb
- https://zh.wikisource.org/zh-hans/梅花易數/卷一

## 1.2 《梅花易数》卷一：物数占

卷一还明确包含“物数占”：

- 看到可以计数的事物，可以用“数量”起数；
- 数量可作为一卦；
- 配合时数得到另一卦；
- 卦数与时数合计再取动爻。

这说明“数字 / 随机数 / 骰子结果”作为现代软件输入是可以找到传统“以数起卦”思想背景的，但“浏览器生成随机数”的具体做法属于现代实现。

来源同上。

## 1.3 《梅花易数》卷一：声音占

卷一还列出“声音占”：

- 听到几声，可按声数起数；
- 也可依据声音来源、方位、物类等取象。

这进一步说明梅花体系本身就强调“外界所见、所闻、所数皆可成为起卦依据”。

本项目暂时不直接申请麦克风权限；可把“声音占”留为后续扩展，例如用户手动点击“我听到 3 声”。

## 1.4 《梅花易数》卷一：字占

《梅花易数》“字占”部分明确提出：
- 字数均匀时可以平分；
- 奇数时，上部分取较少字，下部分取较多字；
- 十一字以上可按字数处理，并由总数取爻；
- 较短文字的传统方法还涉及笔画、声调等细节。

来源：

- https://ctext.org/wiki.pl?chapter=867487&if=gb&remap=gb
- https://zh.wikisource.org/zh-hans/梅花易數/卷一

因此软件 v2 可以先做**“长文本字数起卦”**，避免在没有可靠笔画表、古音表时伪造短字占算法。

## 1.5 《梅花易数》卷一：验色占、形物占

卷一另有“形物占”和“验色占”。

常见颜色类象：
- 青 / 青绿 → 震；
- 红 / 紫 / 赤 → 离；
- 黄 → 坤；
- 白 → 兑；
- 黑 → 坎。

同卷的“八卦类象”还列出更丰富的颜色、物类、形状对应；这些对应并不是一张“八种颜色唯一映射八卦”的统一现代色表，存在重叠，因此软件不应硬造“一色唯一对应八卦”的假传统。

来源：

- https://ctext.org/wiki.pl?chapter=867487&if=en
- https://ctext.org/wiki.pl?chapter=867487&if=gb&remap=gb

## 1.6 《说卦》与八卦自然象

《周易·说卦》提供大量八卦象类，如：
- 乾：天
- 坤：地
- 震：雷
- 巽：风
- 坎：水
- 离：火
- 艮：山
- 兑：泽

因此移动端非常适合做“八象卡片”：
`天 / 泽 / 火 / 雷 / 风 / 水 / 山 / 地`

来源：

- https://ctext.org/book-of-changes/shuo-gua

## 1.7 三枚铜钱起卦

现代易学实践中很常见的三枚钱法：
- 一次投三枚，得到一爻；
- 连续六次；
- 第一次是初爻，自下而上；
- 每枚硬币固定取值 2 或 3；
- 三枚之和得到 6 / 7 / 8 / 9；
- 常见约定：
  - 6 = 老阴，阴，动
  - 7 = 少阳，阳，静
  - 8 = 少阴，阴，静
  - 9 = 老阳，阳，动

不同资料对“哪一面记 2 / 哪一面记 3”可能有不同约定，因此本项目必须在设置中固定一种，并在历史记录中保存 convention。

参考：
- https://www.oracleofchange.com/liuyao/three-coin-method-liuyao-i-ching
- https://ichingoracle.space/zh-hans/i-ching-coin-method/
- https://yiatlas.com/zh/qi-gua

## 1.8 浏览器的秒级时间输入

HTML `datetime-local` 的 `step` 单位是秒，默认 `step=60`，也就是默认粒度为一分钟。

因此当前项目如果要让用户手工选到秒，应至少设置：

```html
<input type="datetime-local" step="1">
```

并把默认值保留到 `YYYY-MM-DDTHH:mm:ss`，不能再 `.slice(0, 16)`。

参考：
- https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/datetime-local
- https://developer.mozilla.org/zh-CN/docs/Web/HTML/Reference/Elements/input/datetime-local

## 1.9 浏览器随机数

虚拟随机数、虚拟骰子、虚拟硬币不应使用 `Math.random()` 作为核心随机源。

Web Crypto 的：

```ts
crypto.getRandomValues(...)
```

可以提供更强的随机值，并且浏览器支持成熟。

参考：
- https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues
- https://developer.mozilla.org/zh-CN/docs/Web/API/Crypto/getRandomValues

# 3. 起卦方式一：秒级时间起卦

## 3.1 为什么当前版本不够精细

传统“年月日时”里的“时”，通常是时支层面的“时辰”，不是现代钟表的秒。

所以：
- “精确到秒”不是古籍原始规则；
- 但作为现代数字化扩展是合理的产品需求；
- 必须明确标为“秒级扩展版”。

## 3.2 推荐规则：`meihua_time_second_v2`

保留传统核心：

```text
A = 年支数 + 农历月数 + 农历日数
B = A + 时支数
```

新增：

```text
P = 分钟 × 60 + 秒
```

然后：

```text
上卦 = mod8(A)
下卦 = mod8(B + P)
动爻 = mod6(B + P)
```

其中：

```text
mod8: 余 0 视为 8
mod6: 余 0 视为 6
```

这样做的特点：
- 年、月、日、时仍然保留传统框架；
- 分、秒作为一个“附加数”；
- 每一秒都真正参与最终结果；
- 同一时辰、同一分钟内，不同秒可以产生不同下卦和动爻；
- 算法非常简单，可复现。

必须保存：

```ts
{
  ruleVersion: 'meihua_time_second_v2',
  minute: 39,
  second: 27,
  secondOfHour: 2367,
  traditionalBaseA: ...,
  traditionalBaseB: ...
}
```

## 3.3 UI

显示实时钟：

```text
2026-09-17 21:39:27
```

每秒刷新。

用户点击“锁定此刻并起卦”时：
- 立即冻结那一秒；
- 后续页面不要继续变；
- 历史保存精确 ISO 时间。

手工修改时间时：
- `datetime-local step="1"`
- 默认值到秒；
- 明确显示时区。

# 4. 起卦方式二：随机数起卦

规则名：

```text
meihua_random_numbers_v1
```

## 4.1 随机来源

用：

```ts
crypto.getRandomValues()
```

不要用：

```ts
Math.random()
```

## 4.2 推荐输入

一次生成三个整数：

```text
N1, N2, N3 ∈ [1, 9999]
```

## 4.3 起卦

```text
上卦 = mod8(N1)
下卦 = mod8(N2)
动爻 = mod6(N1 + N2 + N3)
```

## 4.4 可重现

历史必须保存三个原始数：

```json
{
  "numbers": [1386, 7421, 519]
}
```

不能只保存最后卦名。

## 4.5 UI

显示：

```text
随机数一：1386
随机数二：7421
随机数三：519
```

按钮：
- “生成”
- “确认并起卦”

用户确认后锁定，不要自动重新生成。

# 5. 起卦方式三：摇骰子

规则名：

```text
meihua_dice_v1
```

这是**现代交互方式**，不要称为古籍原法。

为了让 8 个经卦机会对称，推荐：

```text
八面骰 d8 × 2
六面骰 d6 × 1
```

一次“摇骰子”得到：

```text
D1 = 1..8
D2 = 1..8
D3 = 1..6
```

直接：

```text
D1 → 上卦
D2 → 下卦
D3 → 动爻
```

对应：

```text
1乾 2兑 3离 4震 5巽 6坎 7艮 8坤
```

优点：
- 不需要再取模；
- 上、下卦各 8 种完整覆盖；
- 动爻 6 种完整覆盖；
- 用户容易理解；
- 可生成 8×8×6 = 384 种“卦 + 动爻”组合。

虚拟骰子依旧用 `crypto.getRandomValues()`。

同时允许：
- “虚拟摇骰”
- “我有实体骰子，手工输入”

历史保存：

```json
{
  "dice": {
    "upperD8": 5,
    "lowerD8": 2,
    "movingD6": 4
  }
}
```

# 6. 起卦方式四：三枚钱六爻

规则名：

```text
liuyao_three_coins_v1
```

这是六爻模式，不走“梅花单动爻”逻辑。

## 6.1 六次投掷

每一爻投三枚：

```text
正面 = 3
反面 = 2
```

三枚求和：

| 和 | 类型 | 阴阳 | 动静 |
|---:|---|---|---|
| 6 | 老阴 | 阴 | 动 |
| 7 | 少阳 | 阳 | 静 |
| 8 | 少阴 | 阴 | 静 |
| 9 | 老阳 | 阳 | 动 |

第一次投掷：
- 初爻；
- 位于最底部。

第六次：
- 上爻。

## 6.2 转换给现有引擎

```ts
6 -> yin=0, moving=true
7 -> yang=1, moving=false
8 -> yin=0, moving=false
9 -> yang=1, moving=true
```

然后直接复用现有：

```ts
runLiuyao(input, lines, movingMask, ...)
```

## 6.3 虚拟 + 实体两种模式

虚拟：
- 每枚钱用 secure random bit；
- 做视觉翻转动画；
- 六轮进度明确。

实体：
- 用户手工选择三枚结果；
- 或直接录入 6/7/8/9。

## 6.4 历史保存

不要只保存 6 个最终值；最好连 18 枚硬币结果也保存：

```json
{
  "throws": [
    { "coins": [3,2,3], "sum": 8 },
    ...
  ]
}
```

# 7. 起卦方式五：文字 / 字数起卦

规则名：

```text
meihua_text_count_v1
```

## 7.1 v1 建议只实现“十一字以上”路线

传统短字占涉及：
- 单字左右笔画；
- 声调；
- 传统笔画体系；
- 古今字体差异。

如果没有专门核验的数据集，不要让程序自己猜笔画。

因此 v2 首先支持：

```text
11–100 个有效文字单位
```

## 7.2 文本来源

默认：
- 直接使用“所问之事”。

也允许：
- 用户另外输入一句“起卦文字”。

## 7.3 文本归一化

建议：

1. Unicode NFKC；
2. 去掉空白；
3. 去掉纯标点；
4. 保留汉字、字母、数字；
5. 使用 `Intl.Segmenter(..., { granularity: 'grapheme' })` 统计“用户感知字符”；
6. 若旧浏览器不支持，提供本地 fallback。

## 7.4 奇偶拆分

有效字符数：

```text
N
```

若 N 为偶数：

```text
upperCount = N / 2
lowerCount = N / 2
```

若 N 为奇数：

```text
upperCount = floor(N / 2)
lowerCount = ceil(N / 2)
```

对应古法“少者为上，多者为下”的思路。

然后：

```text
上卦 = mod8(upperCount)
下卦 = mod8(lowerCount)
动爻 = mod6(N)
```

必须在结果页显示：

```text
原文本：……
归一化后：……
有效字数：23
上段：11
下段：12
```

# 8. 起卦方式六：外应起卦（颜色 / 物象 / 方位）

规则名：

```text
meihua_external_omen_v1
```

这是最适合做成手机“直觉选择卡片”的传统启发方式。

## 8.1 颜色

传统《梅花易数》可明确核对的颜色映射：

```text
青 / 青绿 → 震
红 / 紫 / 赤 → 离
黄 → 坤
白 → 兑
黑 → 坎
```

注意：
- 这不是完整“8 色 = 8 卦”表；
- 乾、巽、艮等在不同“八卦类象”资料中也可见其他颜色描述；
- 所以不要强造八色唯一映射。

## 8.2 八象

为了完整覆盖八卦，优先推荐用户选自然意象：

```text
天 → 乾
泽 → 兑
火 → 离
雷 → 震
风 → 巽
水 → 坎
山 → 艮
地 → 坤
```

UI 可以把八象做成非常漂亮的八张卡片。

## 8.3 方位

用户再选“这个外应来自哪个方向 / 你直觉最强的方向”：

```text
西北 → 乾
西   → 兑
南   → 离
东   → 震
东南 → 巽
北   → 坎
东北 → 艮
西南 → 坤
```

## 8.4 推荐合成

```text
上卦 = 外应（颜色或八象）对应卦
下卦 = 方位对应卦
动爻 = mod6(上卦先天数 + 下卦先天数 + 时支数)
```

这套“外应 + 方位 + 时数”的软件规则需要标记为：

```text
传统外应思想 + 本项目 v1 规范化实现
```

不能写“古籍唯一公式”。

# 9. 六源合参（实验模式）：真正把“6 个起卦点”合在一次流程里

规则名：

```text
six_source_hybrid_v1
```

显示名：

```text
六源合参 · 实验
```

这是本项目的**现代实验模式**，不是单一传统流派。

## 9.1 六个起卦点

一次流程依次采集：

### 点 1：秒级时间
保存：
- 年月日时分秒；
- `secondOfHour`。

### 点 2：随机数
生成一个 secure integer。

### 点 3：骰子
摇一个 d8 + 一个 d6，或保存完整骰子结果。

### 点 4：颜色 / 八象
用户凭直觉选择。

### 点 5：文字
使用问题文本有效字数。

### 点 6：三枚钱一次
得到 6 / 7 / 8 / 9。

## 9.2 不要偷偷“AI 混合”

六个源必须被代码明确合成，不能把六项文本交给模型让模型“感觉一下”。

## 9.3 推荐的工程合成方式：稳定 canonical payload + 本地 hash

先构造稳定 JSON：

```ts
interface SixSourcePayload {
  version: 'six_source_hybrid_v1'
  exactTime: string
  secondOfHour: number
  randomNumber: number
  dice: { d8: number; d6: number }
  omen: {
    kind: 'color' | 'symbol'
    value: string
    trigramNumber: number
  }
  text: {
    normalized: string
    graphemeCount: number
  }
  coin: {
    coins: [2|3, 2|3, 2|3]
    sum: 6|7|8|9
  }
}
```

然后以**固定字段顺序**序列化。

建议写一个纯 TypeScript 稳定 hash 函数（例如经过测试的 32-bit FNV-1a 多轮派生），得到三个整数：

```text
H1
H2
H3
```

最终：

```text
上卦 = mod8(H1)
下卦 = mod8(H2)
动爻 = mod6(H3)
```

为什么不直接让六项相加：
- 字段尺度完全不同；
- 秒值、随机数可能压过颜色编号；
- 稳定 hash 更容易保证“每个字段都有贡献”。

为什么不依赖远程服务：
- 项目本来就是本地、离线、确定性；
- hash 可纯本地执行。

历史必须保存：
- 六项原始输入；
- canonical string；
- hash 结果；
- 最后卦数。

这样用户点击“为什么是这个卦”时，可以完整展开。

## 9.4 一个更有仪式感的 UI

六步流程：

```text
1 此刻
2 随机
3 摇骰
4 取象
5 文字
```

# 13. 随机数实现：避免 modulo bias

如果要生成 1..N 的均匀随机整数，最好做 rejection sampling，而不是简单：

```ts
raw % N
```

推荐：

```ts
function secureRandomInt(min: number, max: number): number {
  const range = max - min + 1
  const limit = Math.floor(0x100000000 / range) * range
  const buf = new Uint32Array(1)

  while (true) {
    crypto.getRandomValues(buf)
    const x = buf[0]
    if (x < limit) return min + (x % range)
  }
}
```

这样：
- d6；
- d8；
- coin bit；
- 1..9999

都可以统一使用。

# 14. 秒级时间的前端实现注意

当前项目常见写法：

```ts
toISOString().slice(0, 16)
```

只能得到：

```text
YYYY-MM-DDTHH:mm
```

v2 至少要：

```ts
slice(0, 19)
```

并设置：

```html
step="1"
```

但更重要的是：
- 不要把带时区的 ISO 与本地 `datetime-local` 生硬互转；
- 建议写 `formatDateTimeLocalSeconds(date)` 和 `parseLocalDateTime(...)`；
- 避免浏览器时区 + `toISOString()` 造成小时偏移；
- `buildCalendarContext` 继续统一处理时间。
